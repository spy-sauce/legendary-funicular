Runtime flow — one request, end to end

The TEMPORAL path (what happens, in order) — complement to the structural diagram. Follows a single intent from iMessage all the way to the capability call and back home.

Front door Triage Tier-2 agent (Mycelium) Bus Adapter Capability (beyond the adapter) Return path
Front door
1

📱 Inbound message arrives

"Find me 3 suppliers for X and draft outreach." iMessage handler wraps it as an intent nutrient, stamps identity + reply channel + a fresh trace_id, sets a budget_cap from the caller's tier.

POST bus ← { intent, identity, reply_to:"imsg:+1305…", trace_id:7f3a, budget_cap:$5 }
Triage
2

🚦 Triage sizes & routes (does NOT compose)

Classifies depth. Needs 2 capabilities combined, known shape → Tier 2, composed task. Triage does not orchestrate — it matches the request to a pre-defined contract-bound agent and routes to it. Under budget_cap → no spend-gate prompt.

cap-reg match → agent:"supplier-outreach" (contract: comp-intel → draft)
↳ If triage had sized this as build-anything, it would estimate cost, fire the spend-gate back over the front door ("build X, ~$Y, go?"), and only on approval spawn a Mycelium cultivation (steps 3–6 then repeat per leaf).
Tier-2 agent
3

🧬 Contract-bound agent composes (Mycelium, not triage)

The supplier-outreach agent owns the orchestration. Per its NUTRIENTS contract it emits two request nutrients onto the bus and will combine their results. trace_id rides along so every hop is observable on the dashboard.

agent emits → nutrient[supplier-search]→comp-intel · nutrient[draft]→draft (parallel)
Adapter
4

🔌 Adapter translates bus → native call

The HTTP-service transport adapter turns the bus nutrient into the call the real service expects, using comp-intel's interface descriptor from cap-reg (endpoint + request schema). Adapter knows transport; cap-reg supplies the interface. Same adapter serves any HTTP capability.

descriptor(comp-intel) ⇒ POST http://127.0.0.1:9118/company { name:"X" }
Capability
5

🛠️ Capability does the real work (beyond the adapter)

frank-comp-intel runs its OWN internal pipeline — fans out to Glassdoor/Levels/Blind, hits its fallback chain if a source is down, maybe queries a RAG. The bus & adapter don't see any of this; the capability is a black box that takes a request and returns a result. THIS is the "and the calls beyond that" you asked for.

comp-intel internal: source A → source B (fallback) → dedupe → RAG enrich → result
Return
6

↩️ Result nutrient flows back to the agent

Adapter wraps the native response as a result nutrient (same trace_id). Bus delivers it back to the Tier-2 agent. Budget ledger decrements actual spend. If the capability errored/timed out → an error nutrient instead, and the agent (per contract) decides: retry, fallback, or surface the failure.

{ result, trace_id:7f3a, cost:$0.12 } → bus → agent
Compose
7

🧩 Agent composes → triage replies home

The Tier-2 agent waits for both sub-results (supplier list + draft), composes one coherent answer per its contract, and hands it to triage, which replies via reply_to. The user gets a single reply on the same channel they messaged from. Whole journey is one trace on the dashboard.

agent composes → triage → imsg send +1305… "3 suppliers + a draft: …" (trace 7f3a closed)
